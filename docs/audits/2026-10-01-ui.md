# Telegram MCP UI audit — 2026-10-01

Scope: registration/login/recovery, server Telegram QR and 2FA, MCP connection instructions, permissions, client revocation, account deletion, OAuth entry/consent/error pages, mobile layout, keyboard use and appearance. The product stays a free MCP cabinet with one server Telegram session and full read/write access by default.

| Finding | User impact | Change |
| --- | --- | --- |
| Saving identical permissions submitted a mutation | Working AI clients lost authorization unnecessarily | Equivalent profile/chat sets return without updating policy or revoking grants |
| Rendering replaced form controls | Failed submissions and background refreshes erased input and keyboard position | Preserve draft values, radio selection, focus and text selection within the same account/page/policy context |
| Lists had no loading/error states | Users saw “no connections” before a request finished or after it failed | Separate loading, loaded-empty and error/retry states |
| Client IDs were the only labels | Users could not readily recognize an AI client before revocation | Read registered OAuth display names; retain IDs and safe escaping; omit connections revoked during lookup |
| Startup failures displayed registration | A signed-in user could mistake an outage for a missing account | Explicit outage/retry screen; expired authentication still returns to login |
| Navigation existed only in memory | Reload and browser back did not restore the selected section | Allowlisted section hashes and browser back/forward support; latest navigation wins during loading; automatic transitions replace the section hash |
| Mobile navigation scrolled horizontally | Some of the five sections were hidden | Fixed five-item bottom navigation with safe-area padding; no horizontal overflow at 320 px |
| Small muted text lacked sufficient contrast | Secondary information was difficult to read | Stronger text colors, theme-aware surfaces, readable recovery codes and visible keyboard focus |
| Only light styling existed | System dark appearance was inconsistent | Automatic/light/dark themes; non-authentication preference shared with OAuth pages |
| Connection pages were bare HTML | Approval and error pages looked unrelated to the service | Shared Telegram-style server-rendered entry, consent and recovery pages; mobile layout and no JavaScript required |
| Copy feedback and configuration interrupted reading | Refresh reset scroll and users missed copy confirmation | Reopen details before restoring desktop canvas/mobile document scroll; on-demand configuration and dismissible copy feedback |
| Passwords had no reveal action | Users struggled to verify long passwords and Telegram 2FA | Accessible reveal/hide controls, reset when context changes |
| Account deletion occupied the main account view | Destructive action drew unnecessary attention | Expandable deletion section; password and confirmation still required |

Verification uses actual dashboard code with browser/API boundary fixtures, real gateway/OAuth integration tests and local browser checks at 320, 390 and 1280 px. QR screenshots use local synthetic data, never a real Telegram session. Build, type check, lint, full test suite and live synthetic production OAuth/MCP acceptance are release checks. Production account policies/sessions and other Docker project metadata are compared before and after deployment.

This audit does not claim an accessibility certification or change Telegram/MCP authorization rules. Real Telegram sending is not part of UI verification.
