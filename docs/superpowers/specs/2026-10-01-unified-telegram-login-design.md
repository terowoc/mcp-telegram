# Единый вход через Telegram для Web A, кабинета и MCP

Дата: 2026-10-01. Статус: выбранный сценарий одобрен в чате;
письменная спецификация подготовлена для проверки пользователем.

## Цель и согласованный сценарий

Пользователь хочет убрать повторную авторизацию Telegram для веб-чатов и
MCP. Выбран вариант с отдельными Telegram-сессиями браузера и сервера,
но единым пользовательским сценарием. Сохраняем настоящие чаты Telegram
Web A, постоянный серверный MCP и отдельное подтверждение доступа
каждого AI-клиента. Новым пользователям отдельный пароль TG Bridge не нужен.

Первый вход: «Войти через Telegram» → один QR Web A → явный выбор
«Также подключить MCP» → подтверждение серверной сессии веб-клиентом →
готовый кабинет. Выбор MCP по умолчанию выключен и кратко объясняет,
что сервер сможет работать с Telegram при закрытом браузере. Если
пользователь выбирает только чаты, Web A работает без создания кабинета
или серверной Telegram-сессии. Подключить MCP можно позже той же кнопкой
в разделе MCP, без повторного QR при действующей браузерной сессии.

Один QR не означает гарантированно один ввод Telegram 2FA: Telegram может
потребовать облачный пароль отдельно для серверной сессии. Не сохраняем
и не переносим пароль из первоначального входа Web A. Такой запрос
показывается как продолжение подключения MCP, а не как новый кабинет.

Уже вошедший пользователь выбирает «Подключить MCP к этому аккаунту».
При истечении cookie кабинета тот же механизм подтверждает новый вход
через открытую Telegram-сессию. Новая авторизация не расширяет права MCP.

## Существующая архитектура и протокольная основа

Web A использует GramJS в браузерном worker. Сервер использует другой
GramJS-клиент в выделенном worker и хранит зашифрованную сессию.
`src/saas/auth.ts` сейчас требует логин/пароль для кабинета,
`src/saas/login-attempts.ts` требует готового SaaS user ID до запуска QR,
а `src/http/gateway.ts` отдельно запрашивает пароль в OAuth interaction.

Telegram позволяет авторизованному клиенту подтвердить новый login token:
сервер вызывает `auth.exportLoginToken`, браузер — `auth.acceptLoginToken`,
сервер завершает вход, включая `auth.importLoginToken` при смене DC.
Источники: https://core.telegram.org/api/qr-login и
https://core.telegram.org/method/auth.acceptLoginToken.

Это применение стандартного протокола к нашему сценарию; полноценное
подтверждение на настоящем аккаунте входит в приёмку реализации.
Не копируем MTProto auth key или StringSession между браузером и сервером.
Общие API ID/hash остаются конфигурацией приложения, не доказательством
входа пользователя. Bot Login Widget не заменяет MTProto-доступ к чатам.

## Компоненты и поток авторизации

Добавляем координатор временных Telegram-входов перед созданием SaaS
пользователя. Он владеет попыткой, сроком действия, временным worker,
результатом серверного `getMe` и однократным завершением. Он не выполняет
MCP-инструменты и не получает доступ к данным существующего пользователя.

1. После явного выбора MCP браузер создаёт попытку на нашем HTTPS origin.
   Сервер выпускает случайную HttpOnly bootstrap cookie и CSRF token;
   повторный запрос не заменяет действующую попытку незаметно.
2. Временный worker создаёт собственный ключ Telegram, экспортирует token
   и возвращает его координатору по приватному IPC. Координатор выдаёт
   актуальный token только браузеру, владеющему попыткой.
3. Браузерный GramJS worker подтверждает token через `auth.acceptLoginToken`.
   Вызов получает token только от нашего API, а не из query, произвольного
   сообщения окна или пользовательской ссылки.
4. Сервер завершает DC migration и, при необходимости, 2FA. Успех включает
   серверный `getMe`; присланные браузером username/ID не определяют владельца.
5. Явный POST завершения эксклюзивно захватывает попытку и подготавливает
   новый либо существующий SaaS user ID. Координатор останавливает временный
   worker до установки сохранённой сессии. Для проверочного входа в уже
   подключённый аккаунт сначала выполняется logout временной авторизации.
6. В транзакции проверяются актуальные identity, account capacity и статус
   владельца, затем создаются необходимые строки аккаунта/identity и
   сохраняется сессия через SessionVault с AAD окончательного user ID.
   Конкурентная смена привязки отклоняет транзакцию; повторное завершение
   не выполняет её заново. Cookie выпускается только после commit и
   погашения попытки. Постоянный worker запускается по текущим правилам.

До окончательного сохранения session string существует только в памяти
процессов; временный worker не пишет в `telegram_sessions` и не создаёт
доступный SaaS аккаунт. При повторном входе в существующий подключённый
аккаунт проверочная сессия не заменяет его работающую MCP-сессию.
Проверочную авторизацию Telegram закрываем через logout; если Telegram
недоступен, гарантируем локальное уничтожение, не обещая удалённый отзыв.

Временные и постоянные workers используют общий лимит мощности, сейчас
два процесса в production. Вход резервирует слот до запуска и возвращает
503 с Retry-After при исчерпании. Смена временного worker на постоянный
не превышает этот лимит. Существующие процессы других пользователей
не останавливаются для освобождения места.

## API и защита попытки

Новые маршруты под `/api/saas/telegram-auth` размещаются до middleware,
требующего готовую SaaS cookie:

| Метод и путь | Назначение |
| --- | --- |
| POST `/start` | Выдать bootstrap context или создать попытку с его CSRF |
| GET `/:id` | Прочитать состояние и актуальный login token владельца |
| POST `/:id/password` | Передать 2FA текущей попытке |
| POST `/:id/complete` | Однократно подтвердить серверную identity и выдать cookie |
| DELETE `/:id` | Отменить попытку и остановить worker |

Первый POST `/start` без bootstrap context только выдаёт cookie/CSRF,
не создавая worker. Второй POST с CSRF запускает попытку. Все изменения
проверяют точный Origin и CSRF. Чтение требует cookie владельца; attempt ID
в URL сам по себе ничего не разрешает. Bootstrap token не попадает в URL,
localStorage или JSON. Secure/HttpOnly/SameSite=Lax, Cache-Control=no-store.

Срок попытки — пять минут; token обновляется согласно Telegram expiry.
Одна активная попытка на bootstrap context. Ограничение старта — пять
попыток за 15 минут на IP и 20 в час для сервиса; общая worker capacity
остаётся главным пределом. Опрос — не чаще одного раза в две секунды,
лимит 60 запросов в минуту на context. Неверный 2FA — максимум пять
попыток; затем попытка уничтожается. Размер JSON до 8 KiB.

После завершения, истечения, отмены или перезапуска приложения попытка
не восстанавливается. Поздний worker success не создаёт аккаунт, cookie
или сохранённую сессию. При параллельном complete допускается только один
победитель. Token, session string и 2FA не выводятся в логи/ошибки.

## Identity, существующие аккаунты и миграция

Отдельная таблица `telegram_identities` связывает проверенный числовой
Telegram user ID и SaaS user ID с уникальностью обоих значений. Username
остаётся отображаемым атрибутом, не ключом входа. Привязка сохраняется
при отключении MCP; смена Telegram-аккаунта не переназначает её автоматически.

Новые аккаунты имеют nullable password hash, внутренний уникальный login
для совместимости API и счётчик версии credentials. Не создаём фиктивный
известный или случайный пароль и не требуем recovery codes для обычного
Telegram-входа. Повторный вход требует свежего серверного доказательства
владения Telegram, даже если сохранённая MCP-сессия ещё существует.

Существующие password accounts, recovery codes, политики, sessions и
grants сохраняются. Telegram identity связывается с legacy кабинетом
только при явном выборе и действующей cookie плюс свежем подтверждении
старого пароля. Если legacy аккаунт уже содержит серверный Telegram,
проверенный ID должен совпасть. При конфликте identity с другим кабинетом
операция отклоняется; автоматического объединения или переноса прав нет.

Если анонимный вход обнаруживает непривязанный legacy аккаунт с тем же
сохранённым Telegram ID, показываем «Связать существующий кабинет» и
запрашиваем его вход. Не создаём молча новый профиль поверх старого и
не раскрываем логины потенциальных владельцев. Дубли legacy accounts
требуют явного выбора владельцем своего кабинета с паролем.

SQLite schema version повышается с 2 до 3 транзакционно. Миграция
nullable password hash сохраняет foreign keys и все текущие строки.
Новые credential bindings используют счётчик версии. Legacy аккаунты
с нулевой версией сохраняют нынешнюю привязку к password hash до первой
смены credentials или явного связывания Telegram. Это сохраняет текущий
OAuth до перехода. Переход, password recovery, удаление и отключение
аккаунта отзывают прежние browser sessions и grants; обычный повторный
вход в уже связанный аккаунт этого не делает.

Изменить закреплённый Telegram ID через обычное переподключение нельзя.
Legacy login/recovery остаются доступны как путь переноса и восстановления,
но recovery не позволяет присвоить Telegram identity другого кабинета.

## OAuth и единый вход в ChatGPT

Gateway получает дополнительный интерфейс проверки текущей SaaS cookie.
При login interaction с действующей cookie показывает выбранный аккаунт
и продолжает вход по защищённому POST без повторного пароля. При отсутствии
cookie переводит пользователя на единый вход Web A и возвращает к
исходному interaction после завершения. Для legacy пользователей остаётся
ссылка на вход с прежним паролем.

OAuth continuation хранится на сервере и привязан к bootstrap context,
interaction UID и client ID. Браузеру не разрешается задавать произвольный
return URL. Используются только текущие незавершённые interaction нашего
провайдера. Смена/удаление аккаунта, истёкший interaction или изменение
credentials требуют нового потока, без повторного использования old UID.

`prompt=login`/ограничение давности требуют свежего подтверждения Telegram;
`prompt=none` не запускает интерактивный вход. PKCE, DCR, audience/resource,
проверки Origin/CSRF и callback CSP сохраняются. Consent отдельного клиента
показывает Telegram-аккаунт и действующую политику; единый вход не означает
автоматического разрешения ChatGPT. Профиль новых пользователей — чтение.

## Web A и ошибки

Настройка подключения MCP сохраняется до завершения первоначальной
авторизации и не переживает явную отмену. После готовности Web A запускаем
bridge только при согласии пользователя. Добавляем `auth.acceptLoginToken`
в список генерируемых TL методов через штатный генератор; исходную схему
Telegram вручную не меняем. Все вызовы идут через API worker, а не из UI.

Панель MCP заменяет основной login/register form кнопкой входа через
текущий Telegram и оставляет legacy вход по ссылке. Показываем настоящие
состояния: подключение, проверка, 2FA, готово, истёкло, отменено, лимит.
При смене браузерного аккаунта на другой закрываем MCP-панель текущего
кабинета, отменяем попытку и требуем вход для нового аккаунта. Сервер
не переносит cookies, grants или Telegram-сессию вслед за переключением.

Выход из Web A отзывает текущую cookie кабинета и отменяет bootstrap
attempt; постоянный MCP продолжает работу согласно выданным grants.
При переключении браузерного аккаунта также отзывается текущая cookie,
а затем требуется новое доказательство входа. «Отключить MCP» отдельно
останавливает серверный worker, удаляет его сохранённую сессию и отзывает
grants, сохраняя identity для повторного входа в тот же кабинет.

Сбой MCP не блокирует браузерные чаты. При token expiry получаем свежий
token в пределах той же попытки; при отказе Telegram показываем понятную
ошибку и явный повтор. При невозможности bridge сохраняем ручной QR
как обозначенный запасной путь, без заявления об успешном едином входе.
Мобильное оформление, темы и локализация следуют существующему Web A.

## Проверка и deployment

Backend проверки покрывают подделку browser ID, cookie/CSRF, чужие попытки,
повтор complete, late success, два параллельных входа одной identity,
2FA/expiry/cancel, общий worker budget, legacy conflict, schema migration,
credential revocation и OAuth continuation/consent. Frontend проверяется
существующими TypeScript/SCSS/lint командами и реальным браузером согласно
`apps/web/AGENTS.md`, без добавления frontend test files.

Локальный HTTPS browser probe проверяет новый и существующий аккаунт,
открытый Web A, переключение пользователя и ChatGPT OAuth с PKCE. Подмена
Telegram в probe не считается проверкой настоящего Telegram login.
Человек выполняет приёмку с одним настоящим QR и 2FA при необходимости;
проверяем совпадение серверного ID и работу MCP при закрытом браузере.
Тестовые сообщения в настоящие чаты не отправляем.

GitHub Actions остаётся только build → deploy. Перед интеграцией запускаем
нужные проверки локально. Deployment использует текущий immutable GHCR
image и scoped Compose для `mcp-telegram`. Snapshot обоих auth stores,
Compose/env и стабильного ключа позволяет откатить schema v3 вместе с
образом; отдельно проверяем такой откат на изолированной fixture.
Сторонние Docker проекты и их конфигурации не меняются.

## Границы и критерии готовности

Не переносим чаты на backend, не добавляем внешний identity provider,
не объединяем разные legacy кабинеты и не реализуем смену закреплённой
Telegram identity. Секреты пользователя не включаются в документ или код.

Готовность: новый пользователь сканирует один QR Web A, явно включает MCP,
получает кабинет без пароля TG Bridge и подключает AI-клиент через consent.
Уже вошедший пользователь не сканирует второй QR при работающем bridge.
Серверный Telegram ID определяет владельца; ни один путь не выдаёт cookie
по неподтверждённому ID браузера. Legacy данные сохранены, лимит workers
соблюдается, а production deploy и coherent rollback проверены.
