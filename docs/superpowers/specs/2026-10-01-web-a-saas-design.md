# Бесплатный SaaS: Telegram Web A и MCP

Дата: 2026-10-01. Статус: одобрено пользователем, реализация выполняется.

## Требования пользователя

Бесплатный SaaS с открытой регистрацией. Каждый пользователь подключает
свой Telegram. Интерфейс похож на Telegram Web, содержит настоящие чаты
с чтением и отправкой сообщений и отдельный раздел MCP. Пользователь
разрешил использовать открытый код Telegram.

Размещение на существующем VPS, домен `tg-mcp.azimboev.uz`, деплой через
GitHub Actions. Остальные проекты VPS сохраняют свои конфигурации.

## Выбранная основа

Форк Telegram Web A: https://github.com/Ajaxy/telegram-tt.
Исследованный upstream commit: `28ffcf710b15571e5a2f7bb3bdce3fc90fc8ec80`.
В реализации используется зафиксированный commit, а не плавающий master.
Исходники интерфейса, лицензия GPL-3.0, сведения об upstream и наши
изменения находятся в отдельном каталоге `apps/web` с собственным lockfile.
Ссылка на соответствующие исходники и лицензию доступна из интерфейса.
Существующий backend сохраняет свои уведомления MIT; заимствованный
frontend не маркируется как MIT. Продукт имеет собственное название и
оформление, без заявления, что это официальный клиент Telegram.

Сохраняем браузерный MTProto и существующий интерфейс Web A. Перенос всех
чатовых операций на наш Node backend потребовал бы замены его модели
данных, кеша и обработки обновлений. Такой перенос не входит в этот дизайн.

## Две независимые авторизации

Web A соединяется с Telegram в браузере и хранит свою авторизацию согласно
upstream. Сервер MCP получает отдельную Telegram-сессию после явного QR
подключения в разделе MCP. Серверная сессия нужна для работы MCP, когда
браузер закрыт. Сессии и auth keys браузера не экспортируются на сервер.

В интерфейсе раздельно показаны «Чаты» и «Подключение MCP». Вход в чаты
не означает автоматическое предоставление серверу доступа к Telegram.
На подтверждении MCP подключения указано, какой аккаунт сервер будет
обслуживать и что выбранные клиентские права позволяют делать.
Несовпадение браузерного и серверного аккаунтов обозначено явно; сервер
доверяет только аккаунту, подтверждённому собственной MTProto-сессией.
При переключении аккаунта Web A прежний MCP доступ автоматически не
переназначается новому аккаунту.

Telegram API credentials frontend задаются явными публичными build inputs.
Серверный env, пароли, OAuth signing keys и Telegram-сессии не попадают в
frontend build. По явному решению владельца от 2026-10-01 браузер и сервер
используют предоставленные им API ID и hash одного приложения; браузерный
hash будет публичным. Сборка по-прежнему не наследует серверное окружение.
Никакие тестовые upstream credentials в release не используются.

## Интерфейс

Сохраняем список чатов, поиск, аватары, историю, отправку текста, upstream
медиа и темы. Добавляем пункт «MCP» в основное меню, открывающий панель в
стиле существующих настроек. На мобильном устройстве панель занимает
экран с кнопкой возврата. Основной язык нового раздела — русский.

Панель MCP содержит:

- Бесплатную регистрацию, вход и выход из SaaS-кабинета.
- Подключение Telegram к серверу по QR и ввод 2FA при необходимости.
- Состояние: не подключён, ожидает сканирования, нужен 2FA, подключён,
  временно недоступен или достигнут лимит мощности сервиса.
- Адрес `https://tg-mcp.azimboev.uz/mcp`, копирование адреса и инструкции
  для совместимых клиентов. Наличие custom MCP в тарифе клиента не обещается.
- Выбор чтения либо чтения и изменения, список разрешённых чатов.
- Список разрешённых OAuth-клиентов и отзыв их доступа.
- Отключение серверной Telegram-сессии и удаление SaaS-аккаунта.

Изменение разрешений подтверждается пользователем, применяется сервером и
инвалидирует прежние разрешения клиентов, требуя нового consent.
Панель не выводит session string или чужие данные. Секретные bearer tokens
не добавляются в URL и инструкции. Все состояния основаны на API, без
фиктивного статуса подключения.

## SaaS backend

Отдельный режим `saas` сохраняет нынешние single-owner `http`, stdio и
daemon. Все публичные запросы в режиме SaaS авторизуются по user ID,
полученному из проверенной cookie или OAuth-токена, а не из аргументов
клиента. Значение `owner` нынешнего gateway не используется для гостей.

SQLite хранит пользователей, хеши паролей и кодов восстановления,
серверные browser sessions, разрешения и состояние подключения. По
умолчанию используется логин и пароль плюс одноразовые коды восстановления:
SMTP и платный identity provider не нужны. Пароли хешируются scrypt;
восстановление отзывает прежние sessions и grants. Cookie — Secure,
HttpOnly, SameSite; операции изменения защищены CSRF и проверкой Origin.
Регистрация, вход, восстановление и QR имеют отдельные лимиты попыток.

OAuth провайдер сохраняет текущие discovery, PKCE, DCR, resource/audience
проверки и отзыв токенов. `/mcp` общий; проверенный accountId выбирает
пользователя, серверный worker и политику. Отключённый либо удалённый
пользователь не может использовать ранее выданный токен. Без Telegram
подключения доступен только статус настройки, а не чатовые инструменты.

## Workers, хранение и лимиты

Для активного пользователя создаётся отдельный Node worker с неизменяемым
user ID, собственной очередью, TelegramService и конфигурацией прав.
Worker не выбирает tenant из параметров tool call. Зависший worker
перезапускается отдельно, сохраняя fail-closed settlement semantics.
Отдельные процессы обеспечивают границу состояния и отказов; это не
обещание изоляции контейнером или ОС от произвольного выполнения кода.
Docker socket не передаётся приложению.

Серверные Telegram-сессии шифруются AES-256-GCM с уникальным nonce и
привязкой ciphertext к user ID; master key хранится отдельно от SQLite
и передаётся только серверу. Шифрование защищает копию хранилища без ключа,
но не компрометацию работающего backend. Пароль Telegram 2FA передаётся
только в текущий login attempt, не хранится в базе, env или логах.

В SaaS-режиме TelegramService использует внедрённое хранилище сессий,
не текущий файловый saveSession. Supervisor расшифровывает только сессию
выбранного пользователя и передаёт её worker через приватный IPC;
обновлённая сессия возвращается для атомарного шифрованного сохранения.
Plaintext session files и legacy migration в этом режиме отключены.
Master key не передаётся workers. QR attempt может перейти в состояние
ожидания 2FA, привязанное к пользователю и attempt ID; истечение или
отмена уничтожает временное соединение и секрет. Recovery code погашается
атомарно, чтобы параллельные запросы не могли использовать его повторно.

Файлы каждого пользователя находятся в отдельном разрешённом каталоге;
проверяются реальный путь, traversal, symlink и размер. Сессии не сохраняются
в каталогах медиа. База SaaS не архивирует тексты переписки. Web A сохраняет
обычный browser cache upstream; интерфейс не заявляет, что кеша нет.

Предлагаемые стартовые defaults: 100 зарегистрированных аккаунтов,
4 активных серверных worker, один Telegram-аккаунт на SaaS-пользователя.
Worker стартуют по запросу и освобождаются после простоя. При исчерпании
мощности запрос получает понятный отказ с повторной попыткой, без
неограниченной очереди. Входящие запросы и размер ответа ограничены
отдельно для каждого пользователя и для сервиса в целом. Defaults
корректируются нагрузочной проверкой в пределах выделенного CPU/RAM.

## Разбиение реализации

1. SaaS foundation: пользователи, browser auth, worker supervisor,
   изоляция, зашифрованные сессии, QR/2FA, user-bound OAuth и права.
2. Web A integration: зафиксированный fork, сборка и branding, панель MCP,
   использование API foundation, мобильное оформление и инструкции.
3. Production integration: совместная сборка frontend/backend,
   staging smoke checks, scoped Compose, snapshots и проверка rollback.

Для первых двух частей нужны отдельные последовательные планы. До
готовности foundation интерфейс может проверяться локально с test fixtures;
публичное подключение всех пользователей к нынешнему single-owner backend
не публикуется.

## Деплой и миграция

Собранный frontend обслуживается на `/`; `/mcp`, `/oauth`, `/api/saas`
и discovery имеют явные маршруты и не перехватываются SPA fallback.
Service worker не кеширует auth, SaaS API или MCP ответы. CSP разрешает
только необходимые frontend assets, workers и upstream Telegram endpoints;
OAuth interaction сохраняет отдельную строгую политику.

Новые users/session stores располагаются внутри snapshot root проекта.
Перед обновлением останавливаются gateway и все его workers, создаётся
согласованная копия состояния. Откат восстанавливает совместимый image
и snapshot. Master encryption key стабилен между деплоями и сохраняется
приватно отдельно; восстановление snapshot не генерирует новый ключ.
Существующие OAuth grants владельца не становятся пользовательскими
grants автоматически. Операторский вход и миграция оформляются отдельно
от публичной регистрации. Изменения касаются только данного Compose и
nginx vhost. По решению владельца от 2026-10-01 GitHub Actions выполняет
только сборку образа и digest deployment. Тестовые workflow отключены;
проверки конфигурации, healthcheck и откат остаются частью деплоя.

## Приёмка

- Текущие backend tests и проверки сборки проходят.
- Два тестовых пользователя получают независимые workers, сессии,
  файлы, права и grants; подстановка user ID и чужого ciphertext отвергается.
- Проверяются expiry/recovery/CSRF, PKCE, отзыв доступа и отказ после
  отключения пользователя. Смена политики отзывает прежние grants.
- QR expiry, 2FA, отмена, восстановление сессии после restart и worker
  limits проверяются с тестовым Telegram transport.
- Browser tests проверяют регистрацию, панель MCP, QR состояния, смену
  аккаунта, светлую/тёмную темы и мобильный размер без нарушения чатов.
- Upstream chat behavior сохраняется; тестовая отправка проверяется mock
  transport. Реальные сообщения требуют отдельного пользовательского
  указания. Live QR подтверждает сам пользователь.
- Production smoke проверяет HTTPS, discovery, отсутствие гостевого
  доступа к owner, готовность, rollback и сохранность других проектов.
- Доступны GPL notices, соответствующие исходники и воспроизводимая
  инструкция сборки изменённого frontend.
